# Задание агенту сотрудника — 0.2.0-preview.3

Этот файл можно целиком передать агенту Codex. Цель: обновить kyvirok, проверить связку 1С → XML УПД → черновик Диадока, вернуть отчёт. Дополнительное расширение 1С для этой схемы не устанавливаем. Нельзя объявлять подписание/отправку готовыми по факту установки или успешного входа.

## 1. Установить обновление и сохранить рабочие настройки

Исходники и готовый сервер: ветка [approved-operations-0.2.0-preview](https://github.com/figura-studio/kyvirok-1c/tree/approved-operations-0.2.0-preview). [Скачать ZIP ветки](https://github.com/figura-studio/kyvirok-1c/archive/refs/heads/approved-operations-0.2.0-preview.zip). Ветка меняется; проверь версию в `package.json` и запиши SHA коммита. Это предварительная сборка, не стабильная 0.1.2.

1. Найди действующую установку, точку запуска MCP, каталог `ONEC_MCP_DATA_DIR` и версию Node.js. Не создавай второе подключение к той же базе. Перед заменой файлов сохрани прежнюю папку программы и конфигурацию MCP. Личные настройки и `.dpapi` не перезаписывай примерами и не загружай на GitHub.
2. Распакуй новую версию в отдельный каталог, предпочтительно на D при наличии диска. Требуется Node.js **24.18 или новее**. Готовая точка входа — `plugins/kyvirok-1c/server.mjs`; устанавливать зависимости для её запуска не нужно.
3. Сохрани прежние аргументы, окружение и каталог настроек; измени только путь к готовому серверу в существующем подключении. Перезапусти MCP-сервер. Установка с нуля описана в [INSTALL.md](INSTALL.md).
4. Выполни `node <путь-к-серверу> --diagnose` с тем же `ONEC_MCP_DATA_DIR`, затем в чате вызови `get_write_policy`, `get_edo_connections`, **`get_edo_workflow`**. Диагностика должна показать `0.2.0-preview.3` или более новую согласованную версию. Локальная диагностика не проверяет сеть или API.

## 2. Проверить 1С и путь получения УПД

Используй адрес базы, полученный от администратора, и учётную запись сотрудника. Локальный HTTP поддерживается; из дома нужен VPN/доступ в корпоративную сеть. Не отключай проверку HTTPS и не публикуй базу в интернет.

Вызови `list_connections`, затем `list_entities` и `describe_entity` для нужных объектов. Убедись, что доступны реализация, счёт-фактура и связанные справочники. Точные имена объектов и обязательные поля бери из метаданных.

Если объекта нет, посмотри в 1С **Администрирование → Синхронизация данных → Настройки стандартного интерфейса OData → Состав** (названия зависят от конфигурации). Сохрани существующие отметки. Добавление нужных объектов выполняй только при имеющемся поручении и правах сотрудника/администратора; не отмечай всю базу. Отдельно нужны права пользователя на эти объекты. Если прав не хватает, сообщи точное название объекта и отказ.

Для записи используй `preview_change` → полный предпросмотр → `apply_reviewed_change`. Проведение — отдельное `preview_document_action` → `apply_reviewed_operation`. Нужна настоящая форма с изначально снятой галочкой; отсутствие формы нельзя заменять ответом агента «подтверждаю». Для первой проверки не проводи и не отправляй реальные документы автоматически. Выбери с сотрудником один согласованный документ.

Открой этот документ в 1С через доступное управление компьютером и установи **фактический** способ получения XML УПД и печатной формы. Не выдумывай название команды выгрузки. Запиши точный путь меню, тип файла, версию формата и результат. OData не вызывает произвольную штатную печать и сам не создаёт XML УПД. Если доступен только PDF, так и сообщи: PDF не заменяет формализованный XML. Реальные клиентские документы в публичный репозиторий и общий отчёт не прикладывай.

## 3. Выбрать доступный путь Диадока

### Вариант А: браузер, вход по почте и одноразовому коду

Это самостоятельный рабочий путь при отсутствии API-доступа. Нужны инструменты управления браузером у агента, а для чтения кода — отдельно разрешённый доступ к нужной почте. Сам MCP-сервер kyvirok браузером и почтой не управляет.

1. Открой [кабинет Диадока](https://diadoc.kontur.ru/) в согласованном отдельном профиле браузера. Если вход уже выполнен, используй эту сессию.
2. Если кабинет предлагает вход по почте, введи адрес сотрудника. При разрешённом пользователем входе и доступе к этому ящику прочитай только свежее письмо, относящееся к начатой попытке входа. Проверь адресата, время и назначение письма; введи код в поле официальной страницы. Код не цитируй в чате, не записывай в файлы или настройки. Не проси постоянный пароль вместо кода. Если почтового инструмента нет, пользователь вводит код сам. Доступ к другим ящикам сам по себе не разрешает чтение нужного.
3. Если сайт запросил иной способ входа, CAPTCHA или действие человека, следуй фактическому интерфейсу и возможностям среды; сообщи точный блокер. Не обходи защиту и не извлекай cookies для API.
4. Проверь выбранную организацию. После отдельного согласия на загрузку файла загрузи XML штатной кнопкой кабинета и сохрани как неподписанный черновик, **если интерфейс поддерживает этот вариант**. Остановись до кнопки, объединяющей подпись и отправку. Нельзя выдавать загруженный файл за принятый черновик без проверки результата.
5. Если черновик уже создан по API, найди его по `messageId`, номеру, дате и сторонам, не загружай второй раз. Открой документ/печатную форму для проверки.

### Вариант Б: API Диадока

Вход по почте и коду в браузере **не заменяет OAuth access_token API**. Не пытайся использовать пароль 1С или код письма в качестве токена. Настройка — [EXTERNAL-EDO.md](EXTERNAL-EDO.md).

1. Если OAuth и ящик уже настроены, вызови `diagnose_edo_connection`. Запиши результат без токена. HTTP 401 — авторизация; 402 — доступ/подписка API; 403 — права. Пакет исходящих документов не доказывает наличие API. Успешное чтение не доказывает право записи черновика.
2. Если API ещё не подключён, продолжай проверку браузерного пути. Отдельно подготовь вопрос администратору/поддержке: подключён ли API по договору, какие ограничения и оплата; какое OAuth-приложение разрешено. Не покупай доступ и не регистрируй приложение автоматически.
3. Для импорта администратор/уполномоченный пользователь добавляет `draft.create` и абсолютный `importDirectory` к нужному аккаунту в `edo-policy.json`. Это отдельное разрешение, оно не включено по умолчанию. Выдели каталог только под выбранные XML, перезапусти MCP.
4. Положи штатно выгруженный XML в этот каталог. Вызови `preview_edo_draft` с `account`, `fileName` (только имя файла) и проверенным `recipientBoxId` (GUID). Проверь с человеком ИНН/КПП обеих сторон, документ, все строки и суммы, полный XML и SHA-256.
5. После подтверждения формы `apply_reviewed_operation` сервер передаст XML на распознавание и сохранит **неподписанный черновик**, без отправки контрагенту. Сохрани `operationId`, `messageId` и результат. При `unknown` проверь кабинет вручную: не повторяй загрузку, не меняй байты ради обхода защиты и не удаляй журнал `.edo-drafts`. Локальная квитанция — `get_edo_draft_receipt`; это не текущий удалённый статус.
6. Поддержан один XML титула продавца УПД/счёта-фактуры с однозначным типом, UTF-8/Windows-1251, не более 128 КБ. Полный предпросмотр ограничен 24 КБ; большой/неподдержанный файл обрабатывай штатно в кабинете после согласия, не урезай XML и не обходи ограничения сервера.

## 4. Подпись и отправка

В этой версии подпись и отправку завершает человек в штатном кабинете Диадока. Агент может подготовить документ и открыть нужный экран. Успешный вход по коду не означает наличия ключа электронной подписи. Сертификат в списке и установленный КриптоПро не доказывают работоспособность ключа.

Проверь с сотрудником: кто обычно подписывает; USB-токен/локальный компьютер/сервер/облако; с какого рабочего места; нужна ли МЧД и доступна ли действующая доверенность. PIN и закрытый ключ не запрашивай в чате и не копируй. Перед юридически значимым подписанием передай управление человеку. Если кабинет объединяет «подписать и отправить», явно покажи оба последствия до передачи управления. Разрешение создать черновик не является разрешением подписать или отправить.

Для этой первичной проверки **не отправляй документ контрагенту**. Подтверждение работоспособности подписи/отправки потребует отдельного согласованного документа и действия человека. Если человек позднее завершит отправку, проверь фактический статус в кабинете или `get_edo_document`; не считай нажатие кнопки доказательством доставки.

## 5. Ответ, который нужно вернуть

Для каждого пункта укажи **ПРОВЕРЕНО / НЕ ПРОВЕРЕНО / ОШИБКА**, наблюдаемый результат и следующий конкретный шаг:

- Версия плагина, SHA скачанного коммита, Node.js, появился ли `get_edo_workflow`.
- Конфигурация и платформа 1С; чтение OData; доступные объекты; недостающие отметки/права. Без пароля и полного дампа базы.
- Как именно получается XML УПД и печатная форма: документ 1С, путь меню, формат, размер. Если команды нет — где посмотрели и что доступно вместо неё.
- Выбранный путь: браузер или API. Для браузера: вход по почте/коду сработал ли, есть ли разрешённый доступ агента к нужному ящику, выбрана ли нужная организация. Для API: чтение прошло или точный HTTP-код; отдельно остающиеся вопросы по тарифу/OAuth. Не присылай код, токен, cookies.
- Если согласовали создание черновика: появился ли он, совпадают ли стороны/номер/суммы; `operationId`, `messageId`, SHA-256; при ошибке — шаг и очищенный текст ошибки. XML и реквизиты реальных клиентов не прикладывай без отдельного разрешения.
- Подписант и схема подписи: где ключ, рабочее место, МЧД; что проверено фактически, а что лишь сообщил сотрудник. Подписание/отправка: «не выполнялись» либо отдельное подтверждённое действие человека и наблюдаемый статус.

Не заменяй непроверенный пункт догадкой. Вопросы, которые нельзя выяснить просмотром интерфейса, задай сотруднику кратко и прямо. Если нужного инструмента/права нет, сразу укажи это и продолжи независимые проверки.

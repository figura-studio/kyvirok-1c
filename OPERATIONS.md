# Операции после подтверждения — 0.2.0-preview.1

Это предварительная сборка. Реализованы дополнительные операции OData и клиент HTTP-адаптера 1С. Штатная печать УПД, отчёты и реальные отправки операторам ЭДО **ещё не подключены**: потребуется разработать, установить и проверить адаптер под конкретную конфигурацию. Готового расширения `.cfe` в выпуске нет. Тесты операторов используют имитатор.

## Возможности

| Возможность | Состояние | Что требуется |
| --- | --- | --- |
| Поиск документов, справочников, остатков, оборотов, записей регистров | Есть через OData | Публикация объектов и права пользователя |
| Создание/правка черновика, включая реализацию или счёт-фактуру | `preview_change` → `apply_reviewed_change` | Разрешённые поля, реальные метаданные, обязательные реквизиты |
| Проведение / отмена проведения | `preview_document_action` → `apply_reviewed_operation` | Отдельное разрешение `actions`, опубликованные Post/Unpost и права 1С |
| Пометка удаления / снятие пометки | Тот же порядок | Отдельное разрешение; проведение сначала отменяется отдельным действием |
| Штатная печать УПД, накладных, счетов; получение PDF в чат | Клиент и доставка файлов готовы; серверная печать не реализована | Адаптер под версию конфигурации и БСП |
| Штатные отчёты и создание на основании | Клиент адаптера готов | Реализованная и разрешённая операция расширения |
| 1С-ЭДО, Диадок, СБИС/Saby | Выбор трёх профилей, подтверждения и контракт готовы | Реальные операторские адаптеры, учётные записи и подпись |

Запись полей через OData не заменяет команду «Создать на основании» и не гарантирует автоматическое заполнение всех реквизитов. Создание счёта-фактуры как записи и штатная печать УПД — разные операции.

## Проведение

В существующий `write-policy.json` добавьте `actions` только для согласованных объектов; сохраните старые `create` и `update`. Имя объекта проверьте в метаданных:

```json
{
  "demo": {
    "Document_РеализацияТоваровУслуг": {
      "update": ["Комментарий"],
      "actions": ["post", "unpost"]
    }
  }
}
```

`mark_deletion` и `unmark_deletion` разрешаются отдельно. Физического удаления, автоматического перепроведения и массового выполнения нет. Старые настройки не дают новых прав. После изменения правил перезапустите MCP-сервер.

Предпросмотр проведения содержит документ целиком, сумму, ключ и ожидаемый статус. Будущие бухгалтерские проводки не рассчитываются. После выполнения проверяется статус, а не правильность движений.

Для PATCH используется серверный `If-Match`. Для Post/Unpost атомарная проверка заголовка в документации OData не обещана. Коннектор заново читает DataVersion перед действием и передаёт заголовок, но между чтением и Post остаётся окно одновременного изменения. Это указано и в форме подтверждения. Не проводите так документ, который параллельно редактируют. Для строгой атомарности нужен адаптер с транзакцией и блокировкой в 1С.

## Печать и ЭДО

После установки совместимого адаптера администратор создаёт `bridge-policy.json` рядом с `write-policy.json`. Пример — `bridge-policy.example.json`. **Копирование примера не устанавливает адаптер.**

`servicePath` указывает HTTP-сервис в той же публикации 1С. Используются имеющиеся учётные данные базы. Передача пароля другому серверу и перенаправления запрещены. При редиректе настройте подключение на конечную согласованную публикацию. Поддерживаются корпоративный HTTP и HTTPS.

Профили: `1c-edo` — встроенный 1С-ЭДО; `diadok` — Контур.Диадок; `sbis` — СБИС/Saby. При смене оператора меняется `defaultEdoProvider`; при нескольких операторах укажите `provider` в запросе. Учётные записи организаций и контрагентов определяет адаптер. Перезапустите MCP-сервер после изменения настроек. Переключение этих профилей не требует нового кода коннектора, но соответствующий серверный адаптер должен работать.

Пароли операторов, PIN и закрытые ключи остаются в штатных механизмах 1С/оператора. Подпись и отправка — отдельные действия. Отправка не даёт согласия на подписание.

## Задание агенту сотрудника

1. Вызови `get_write_policy` и `get_capabilities`. Не выдавай наличие имени оператора за готовую интеграцию.
2. Для изменения данных используй `preview_change`, для проведения — `preview_document_action`, для штатной печати и ЭДО — `preview_business_operation`. Названия и параметры бизнес-операций бери из `get_capabilities`.
3. Покажи весь предпросмотр. Создание, проведение, подпись и отправка требуют отдельных форм. Не расширяй права автоматически.
4. Вызови соответствующий `apply_reviewed_*` и дождись настоящей формы MCP с изначально снятой галочкой. Текстовое «да» не подменяет отсутствующую форму.
5. Для ЭДО покажи оператора, отправителя/получателя с ИНН и ящиками, документы, суммы, файлы и подписанта. Сначала отдельное подписание, затем отправка уже подписанных документов.
6. При `unknown` не повторяй запись/отправку. Для адаптера вызови `get_operation_status` с `planId`; после перезапуска ищи этот план в журнале 1С. Для OData прочитай документ и проверь движения.
7. Файлы доступны по `localPath` и MCP URI `kyvirok-1c://artifacts/...`. Покажи ссылку пользователю. Встроенный просмотр зависит от клиента. Каталог задаётся абсолютным `KYVIROK_1C_ARTIFACTS_DIR`, например на D. По умолчанию это `artifacts` в папке настроек. Ограничения: 20 МБ на файл, 100 МБ за сеанс. Автоматического удаления файлов нет.

Для установки серверной части нужны точный релиз конфигурации, платформа, версия модуля ЭДО, способ подписи и возможность публикации HTTP-сервисов расширения. Пароли в переписке не нужны. [Контракт и критерии проверки](BRIDGE.md).
